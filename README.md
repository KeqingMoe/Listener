# Listener

一个用 TypeScript 写的 QQ AI 猫娘，通过 OneBot v11 接入 QQ，使用支持工具调用的 OpenAI 兼容接口。

支持多个白名单群，每群独立 Listener 实例和记忆。支持 @／引用接话、随机插话、群内共享记忆、分条发送与真实 @，也能查询成员。禁言、解禁、撤回成员消息、改群名片可分别配置为关闭、需要主人确认或自主直接执行，默认关闭；不提供踢人、公告或修改群设置。

## 配置和运行

建议 Node.js 24+，并准备可用的 OneBot v11 WebSocket 服务。

```sh
npm ci
npm run faces:sync  # 获取完整 QQ 原生表情目录（需要联网）
# 仅首次配置；不要覆盖已有文件
cp config.example.toml config.toml
cp .env.example .env
# 编辑配置、填写密钥，再把 config.toml 的 [ai] enabled 设为 true
npm run config:check
npm run build
npm start
```

- `config.toml`：模型、连接、触发概率、记忆与工具开关，不入库；注释见 `config.example.toml`。
- `.env`：仅放 OneBot Token 和模型 Key，不入库；也可用配置中指定名称的环境变量注入密钥，优先于文件。
- `prompts/listener.md`：人设与语气，入库。权限规则不放在人设里。
- 相对人设和记忆路径按 `config.toml` 所在目录解析。未知配置项或非法值会阻止启动，检查命令不联网、不创建记忆库。

旧版 `.env` 可用 `npm run config:migrate` 一次性迁移：保留实际参数，旧文件备份在 `data/config-migration.env.bak`；若已有 `config.toml` 则拒绝覆盖。迁移工具将旧版单群设置写成明确的 `groups` 白名单，不生成 `bot.group_id`；运行时不再从环境变量读取行为参数。

修改配置或人设后重启 Bot，暂不热加载。开发用 `npm run dev`，测试用 `npm test`；不要同时启动多个实例。

## 多群支持

一个进程共享 OneBot 连接、模型客户端、人设和表情目录；每个启用的群都有独立 Listener、SQLite 文件、聊天摘要、回复批次、冷却／随机次数和管理确认状态。图片与转发读取必须核验本群来源，工具缓存不跨实例共享；私聊和未启用群的消息不进入群记忆，不处理命令。请勿为每个群再启动一个 Bot 进程。

```toml
[ai]
# 在现有 [ai] 表内添加，不要重复声明同一张表
max_concurrent_turns = 2

[groups."100000002"]
enabled = true

[groups."123456789"]  # 替换为实际群号；QQ 账号须已经在群里
enabled = true

[groups."123456789".reply]
random_probability = 0  # 这个群只响应明确呼唤

[groups."123456789".images]
enabled = false

# 可选：补充而不是替换全局人设，权限规则仍由程序强制执行
# [groups."123456789".persona]
# append_file = "prompts/group-tech.md"
```

全局设置作为默认值，群表可按字段覆盖 `reply`（含 `random`）、`tools`（含 `moderation`）、`images`、`forward`、`memory`、`attention`，或用 `persona.append_file` 追加本群风格。连接、模型、身份、主人及日志仍是全局配置，群内没有动态修改配置的命令。最多配置32个群，配置／人设变更后执行 `npm run config:check` 并重启。

**`groups` 是唯一的群白名单来源，其中所有 `enabled=true` 的群就是完整白名单**，不会额外启用任何群；未配置 `groups`、空表或全部关闭都意味着不服务任何群。`[bot] group_id` 已移除，配置中保留该字段会报错，请改用明确的群表。现有100000002群继续使用全局 `memory.path`，无需搬迁、清空或重新归属旧记忆；其他群默认使用该路径所在目录下的 `groups/<群号>/listener.sqlite`。可通过每群 `memory.path` 指定独立文件，启动前拒绝路径／符号链接／硬链接冲突；数据库内部绑定群号，错群打开会拒绝，不能靠修改配置把A群库改作B群库。

全局 `ai.max_concurrent_turns` 为1～8，默认2。名额覆盖整个回复批次（含摘要、工具和发送），从而限制模型并发；不是按人排队。每群最多占用／等待一个名额，按先到先得让等待群前进。等待名额时仍继续合批，拿到名额后才固定上下文；新群不会抢断正在处理的批次。单群重置只取消本群的当前／等待批次，断线和进程停止会取消所有群；停止／重连不补发离线消息。

主人仍是同一个固定 QQ；管理能力由本群配置授予 Bot，不依赖发言者是不是主人，普通群管理员不会自动获得确认码审批权。`/reset` 只清空所在群；管理确认码只能由主人在提出操作的同一群确认，不能跨群遥控或确认。跨群共享记忆、自动加群和热加载不在本版范围内。`app.group_ready` 记录各群配置，`group_id` 与 `turn_id` 用于分辨并行群的运行日志。

## 主动关注计划

```toml
[attention]
enabled = true    # 默认关闭；各群可在自己的 attention 表覆盖
max_plans = 16    # 每群并存计划上限，1～32，非发言条数限制
```

模型通过 `manage_attention` 安排何时再看本群：`create` 新增独立计划，`update` 指定 `plan_id` 替换该份，`cancel` 只取消指定计划。一次合批回复多个人可以建立多份等待，绝不以最后一份覆盖整个群。每份计划的 `any_of` 条件是“或”；命中后仅消费该份，其他计划保持原来的截止时间。多个计划同时命中合入同一待处理批次，不逐计划调用模型。

例如下面是一次工具调用参数（QQ号换成真实目标）：

```json
{
  "operation": "create",
  "purpose": "等对方补充版本信息",
  "any_of": [
    {"type": "member_message", "user_ids": ["123456789"]},
    {"type": "after", "delay_seconds": [300, 600]}
  ],
  "expires_in_seconds": 900
}
```

支持条件：`next_message` 等下一条；`member_message` 等指定成员任意一人；`after` 到随机选定的时间回来；`activity` 在 `window_seconds` 内满足 `min_messages` 条且 `min_senders` 个不同成员（缺省1人）。每份最多8个条件，成员条件最多16个QQ号；活跃度最多观察最近512条合格消息。时间以秒设置，有效期最长24小时，必须严格长于定时条件的最大等待时间。时间区间在提交时只抽一次，不随新消息不断推迟。

**随机抽签继续保留**，不需要主动关注也能照常运行；觉得不合适可自行把 `reply.random_probability` 设为0。@／引用、抽签、关注计划统一合批；@／引用不清空其他计划，也不会抢断正在处理的回复。纯关注唤醒也可使用本群已配置的管理能力，但计划文字不能修改能力模式或授权读取其他群。条件只决定何时检查，不代表必须说话，回来后仍可选择 `stay_silent`。

计划操作先在本轮暂存：可以先设置再发言，或在同一次模型响应的工具调用列表里先 `send_message`／`stay_silent` 再设置；只执行其后的关注操作或已启用的 reaction，不再发送第二批消息或执行额外管理操作。仅设置计划不结束本轮，必须正常回复、明确沉默或成功发送管理确认通知后才提交所有有效操作；失败、取消、超时或仅输出正文不提交。被其他事件消费、到期或更新的旧计划不会被本轮过时操作复活，提交结果在下一轮上下文中可见。

新建／更新计划在本轮结束时生效，消息条件只匹配提交后到达的消息；不把分条回复期间已经到达的消息算成未来的“下一条”。定时检查可以读取此前尚未处理的新消息；没有未读消息时不调用模型、不凭空开话题，到点的定时条件会等待新消息直到计划失效。机器人自己发的消息、命令、私聊和其他群不会触发。未读缓存每群最多128条，真正开始新批次才推进阅读进度，超限有省略提示；未核验引用不提前混入。本轮可见计划、剩余时间和命中原因通过 `attention_state` 提供，过长的条件详情明确标注省略，不记录到日志。

计划、未读进度和活动计数均为每群独立的运行期状态；`/reset`、断线、停止或重启清空，不恢复过时期待。未设置计划或计划已到期时，仍靠原有 @／引用和随机入口开启下一轮，不额外启动默认巡查。`attention.wake`／`attention.commit` 日志只记录群、批次、数量和状态，不记录计划内容。

## 回复批次

不逐人排队，也不让后来的人覆盖先前请求：

- 空闲时第一次 @／有效引用开启 `[reply] delay_ms` 收集窗口，补充文字、图片及其他人的呼唤一起交给模型；后来消息不会不断延长窗口。
- 当前批次开始后，上下文、呼唤者和消息读取范围固定，工具调用及分条发送不会被新消息打断。期间的新消息只汇入**一个待处理批次**。
- 当前批次结束，有新呼唤或关注计划命中就合批处理；否则只有普通消息时对这一批进行**一次**随机参与判断，沿用概率、冷却和每分钟次数限制。随机入口没选中就消费该批次，不逐条重抽或之后补抽；启用关注计划时，尚未读过的消息仍可由之后的计划检查。
- 等待窗口已经过去就不重新等整段时间，仍遵守群回复冷却。重置、断线、停止和处理超时仍会取消；需要远程核验的引用未完成时不会混入已开始的批次，核验成功后再加入待处理批次。
- 每批最多保留64条新消息，优先保留最早的明确呼唤，普通消息保留较新的；新批次内容及呼唤者列表合计最多24000字符，超限有明确省略数量／正文截断标记。历史上下文另受记忆配置限制，模型仍可合并回复或保持沉默，不保证逐人逐条回答。
- 普通群员、主人、混合呼唤、随机参与或关注唤醒均使用本群同一份管理能力配置，不要求主人先明确提出请求。来源身份和省略标记仍保留，不能把未核验转发声称的身份当成真实群成员身份或配置授权。

## 自主管理与确认模式

每项管理能力独立配置为以下字符串，省略时默认 `"off"`：

| 模式 | 行为 |
| --- | --- |
| `off` | 不向模型提供该工具，执行层也拒绝调用 |
| `confirm` | Bot 可根据本群上下文自主提出操作，程序发送具体目标与操作内容，等待主人在同群 `/confirm CODE` |
| `direct` | Bot 可自主决定并立即执行，无须主人先发指令或逐次确认 |

```toml
[tools.moderation]
mute = "off"
unmute = "off"
recall = "off"
member_card = "off"
confirmation_ttl_seconds = 60
max_mute_seconds = 600

# 按字段继承全局默认；只为这个群开启相应能力
[groups."123456789".tools.moderation]
mute = "confirm"
unmute = "direct"
```

这是严格的破坏性配置变更：旧 `true`／`false`、大小写变体和其他字符串均报配置错误，包括未启用群中的错误值，不做静默转换。迁移旧配置时必须明确选择模式；若想保留原来的审批要求，旧 `mute=true` 应显式写成 `mute="confirm"` 和 `unmute="confirm"`。本机已有开启项已如此迁移，不会自动提升为直接执行。

模型工具分别为 `mute_member(user_id, seconds)`、`unmute_member(user_id)`、`recall_message(message_id)`、`set_member_card(user_id, card)`。禁言秒数必须为1至本群上限，**0不再代表解禁**；解禁独立调用，不能通过禁言绕过其模式。当前未实现踢人或公告能力，相应配置项仍会报未知字段。

配置是授予 Bot 的自主能力，不是把管理权限转交给说话的群友。模型可判断是否采纳建议，也可以不采取行动；上下文中的命令、昵称、转发和关注计划不能修改模式。执行前仍核验当前群、登录身份、Bot 的实际管理员／群主权限及目标身份；不能操作主人或 Bot 本人，不能禁言／解禁管理员或群主，普通管理员 Bot 不能改管理员名片或撤回管理员消息。撤回目标必须属于本轮冻结的可见消息或其直接引用，并再次向 QQ 核验，已知消息的发送者还必须与冻结记录一致；不会因为模型猜出一个消息ID就开放撤回。

确认码按群隔离，最多10个待确认项，有效期1～60秒，只有主人能确认其他群员或自主关注触发的提案；其他人尝试确认不会消耗有效码。主人确认时再次核验，确认码在异步核验前消耗一次，防止并发重复执行。重置、断线或重启清空待确认项。

沿用每轮最多一项新的管理操作尝试；相同参数的重复调用复用本轮结果，不重复发到 QQ。`executed` 才表示接口确认执行，`confirmation_required` 只是待确认；发出请求后的超时或不明响应为 `unknown`，不会自动重试，也不能宣称成功。同一模型响应里，若前面的管理操作失败或结果不明，后面预先写好的回复会被延后，必须先把结果交回模型再决定说什么，不扫描或拦截具体措辞。直接操作已经生效后，后续模型失败或取消不会回滚。看图／读取转发的结果必须先返回才能决定操作；发送回复或沉默结束后不追加管理操作。审计日志记录动作、群、目标ID及 `request`／`direct`／`confirm` 阶段，不记录确认码或名片文本。

## QQ 原生表情

支持普通和超级表情，与文字、@、引用混排，也可以只发表情。模型在 `send_message` 的 `segments` 中使用 `{"type":"face","id":"375"}`，程序转换成 OneBot `face` 消息段；只开放 ID，不开放 `chainCount`／`resultId`。不另设每条或每轮的表情数量配额，沿用现有每条最多12个片段、每轮 `reply.max_parts` 条及发送节流；关闭 @ 功能不影响表情。

超级表情若要展示大表情效果，建议独占一个 `part`、只放一个 `face`，且不设置 `reply_to`；文字、@ 和引用放到相邻的文字消息。混排和带引用仍允许用于有意的小尺寸展示，程序不擅自拆分，不增加表情数量配额。

模型看到的接收消息、Bot 已发送的历史消息、`read_message` 及 `read_forward` 内容保留有序 `segments`，不再把原生表情、@、图片和转发拼成正文中的人工标记。例如 `[{"type":"text","text":"围观一下"},{"type":"face","id":"271","name":"吃瓜"}]`；`face.name` 是目录提供的辅助说明，发送工具也接受它但不传给QQ，实际表情只由 `id` 决定。未知原生表情保留合法 ID、不猜名称。发送仍只接受已加载目录中的 ID，防止 NapCat 静默丢弃未知表情；Unicode emoji 仍是普通文字，商城表情包和收藏图片不属于此功能。

文字就是文字：`text` 内的 `[QQ表情：…]`、`[at:…]` 或 CQ 样式字符串可以原样引用和讨论，程序既不拒绝这些字样，也不把它们自动升级成真实操作。出站始终使用 OneBot 消息片段数组；[已核对 NapCat 4.18.28 的发送归一化](https://github.com/NapNeko/NapCatQQ/blob/v4.18.28/packages/napcat-onebot/action/msg/SendMsg.ts)，CQ 解码只作用于顶层字符串消息，数组中的 `text` 不会被解码成操作。真正的提及必须用 `at` 片段，并继续核验本群成员、功能开关、数量及禁止全体／自己的限制。收到的 `at.user_id`、`reply.message_id`、`image.image_id` 和 `forward.forward_id` 各自保留类型；媒体引用的 `not_viewed`／`not_read` 不是已读取内容，也不会携带原始URL或转发资源凭证。普通文字中的媒体样式标记不授予新记录的媒体读取能力。

新记录在原有 SQLite JSON 字段中保存经过净化的结构化内容，不改数据库表结构。内部兼容用的旧 `text` 字段不会与新 `segments` 重复交给模型；旧记录无法可靠区分原文和旧标记时，用 `representation=legacy_text` 明示保留，不做正则迁移或自动猜测转换。已有摘要原文不改写，后续摘要输入使用结构化消息；摘要的保留、选取、事务及取消算法不变。内容按序裁剪并用 `content_truncated`／`segments_omitted` 等独立字段说明，不插入冒充原文的截断标记；批次仍受24000字符总预算限制，保留调用者和消息身份。

`npm run faces:sync` 从固定的 NapCat **4.18.28** 来源同步完整目录到 `data/qq-faces.json`，重启后加载，平时收发不联网查目录。未同步时仅有少量独立编写的示例映射；已存在但损坏的目录会明确报错，可重新同步修复。完整上游原文件与许可证保留在被 Git 忽略的 `data/` 下，不随源码分发；上游采用限制性再分发许可，公开打包数据前需另行核对许可。普通和带动画配置的 ID 都可选择，具体动画呈现仍取决于 QQ 客户端。

## 消息表情回应（reaction）

```toml
# 添加到已有 [tools] 表中，不要重复声明同名表
[tools]
reactions = true   # 默认 false；各群可在自己的 tools 表独立覆盖
```

开启后提供 `react_message`，与发送一条 `face` 消息不同，它在目标消息下面添加／取消 Bot 自己账号的表情回应，不额外发送聊天气泡。参数为 `message_id`、`emoji_id`（均为字符串）和 `action`（`add`／`remove`）；底层通过现有 OneBot 连接调用 `set_msg_emoji_like`，转换为 `set: true`／`false`。不需要主人确认，独立于成员查询、@、管理工具开关；关闭功能不删除已经添加的回应。

候选目录直接复用 `faces:sync` 留下的完整 NapCat **4.18.28** 原始资源：`sysface` 的329条使用 `QSid`，`emoji` 的165条使用 `QCid`，合计494条，不人为缩成少数常用表情。工具同时展示名称、类别及 Unicode 字符；不能把 `EMCode`、emoji字符本身或 QQ 内部消息长ID当成参数。目录是候选集合，不保证QQ接受所有项；业务拒绝会反馈给模型，不把外层请求成功当作反应成功。完整上游资源及许可证仍只放在忽略的 `data/`，不嵌入源码。原始资源缺失时仅使用8个独立编写的示例，执行 `npm run faces:sync` 后重启可恢复完整目录；已存在但损坏的资源不静默降级。未启用 reaction 时不加载它的目录。

目标必须在本轮冻结的本群消息范围内，或是这些消息的可核验引用；每次真正变更前都用 `get_msg` 再次核对所属群、消息ID和发送者，即使本地已经缓存也不省略。不能操作私聊、其他群、任意猜测ID或合并转发内部声称的ID；API本身没有群参数，隔离由程序在调用前强制保证。

同一轮可以给多条消息／多个表情回应，不会执行第一项就结束；也可以和文字回复、关注计划合用。`react_message` 和 `manage_attention` 在同一次模型响应中可位于 `send_message`／`stay_silent` 的前后；终止标记之后仍不执行第二次发言或新的读取／管理操作。只回应表情时用 `stay_silent` 结束，表示不再额外发文字。若还要看图或读转发，先接收内容，再在下一次模型响应中决定反应。reaction 即时执行，不像关注计划暂存，后续模型失败／超时／取消不会自动撤销已经执行的动作。

同一轮重复请求同一消息、同一表情的相同最近动作会去重，`add → remove → add` 则按顺序执行。每轮最多32次操作尝试以约束外部调用量，不是每条消息只能回应一个；重复命中缓存不额外消耗。原生返回 `result=0`／`true` 才记为确认成功，明确失败记为拒绝，超时或未知格式记为结果不明。结果不明后本轮不再对该消息／表情重试或反向操作，也不自动重发或回滚。客户端最终显示仍以 QQ 为准。

模型不需要主动想到查询：每次正常思考前，程序会自动采集当前批次和近期可见消息的 reaction，并在 `current_batch`、近期聊天上下文和 `read_message` 返回的对应消息对象旁附上 `reactions`。读取数据来自经过群／消息／发送者核验的 `get_msg.emoji_likes_list`；表情有名称／字符时显示名称／字符，未知ID保留编号，计数不冒充人数。[当前版本 `get_msg` 实现](https://github.com/NapNeko/NapCatQQ/blob/v4.18.28/packages/napcat-onebot/action/msg/GetMsg.ts) 只提供聚合信息，底层未带聚合字段时也会构造空数组。原生快照没有自己的参与标志，因此不会根据历史操作推断“含你”。消息没有该字段表示未取得信息或展示预算不足；`empty_snapshot` 仅表示QQ这次返回的快照未列出反应，不保证真正无人回应；`stale` 表示可能过时，`partial`／`omitted` 标明截断。

采集每群独立缓存最多512个消息、每条展示最多8种表情，按保留期限过期；普通快照15秒内复用。每轮自动刷新最多8条，优先最多4条已收到变更通知的可见消息，随后优先当前问题、最多2条直接引用目标、最近2条自身回复，再考虑本批和近期消息，避免只查看提问消息却漏掉被点赞的 Bot 消息；自动采集最多2个实际未完成请求、总等待预算1.5秒，失败不阻塞正常回复、不把未知清成空。显式 `read_message` 仅按需刷新自己的目标，不顺带扫描其他消息。变更通知只标记缓存待刷新，不根据可能有歧义的通知计数自行加减；本账号的变更也标记快照过时，不盲目加一。WebSocket 客户端通过专用 `notice` 事件转交 `group_msg_emoji_like`，入口沿用群白名单和连接就绪检查；不转交其他 notice。通知不进入聊天历史、未读缓冲或关注条件，不产生新的模型调用。新消息不能扩展已经开始的一轮读取范围；断线／重置／停止后迟到的请求不能恢复已清空的缓存。

标注是模型输入的有界展示层，不修改消息正文、调用者身份或管理权限，不写成伪造聊天记录，也不改变数据库摘要内容和摘要算法。每份批次／历史表示的新增标注预算最多6000字符，批次仍遵守原有24000字符上限，单个读取结果的标注最多1000字符；空间不足时优先展示有实际反应的消息，再优先较新的消息，不让旧空快照挤掉最新有效反应；只省略标注，不挤掉正文或真实调用者，也不改变原消息顺序。

另外，`reaction_state` 提供本群本轮可见消息的近期尝试记录及上一轮的确认／失败／不明结果，不伪造聊天消息写入数据库，也不代表已从QQ读取到当前完整回应状态。同一消息／表情保留最近一次尝试（后来的失败可能替换较早的成功记录）；每群最多128项，按聊天保留期限过滤，重置、断线或重启清空记录，但不撤销QQ上已有的回应。收到 reaction notice 不自动唤醒模型，避免互相点赞循环。日志只记录工具名、状态、计数等元数据，不记录消息正文；纯成功反应的回合记为 `reacted`，不是完全沉默。

### 查询是谁回应的

开启 `[tools].reactions` 也提供只读工具 `get_reaction_users`，独立于群成员查询开关，不需要主人确认。默认仍只自动展示聚合计数；只有用户询问“谁点的／我点了什么”等需要身份信息的问题时，模型才按需查询，不会自动为每条消息拉名单。

参数：`message_id`、`emoji_id`、`emoji_type`（字符串 `"1"` 为QQ表情、`"2"` 为Unicode，使用快照中的类型）；可选 `user_id` 核对特定QQ，及 `cursor` 翻页。按消息和表情查询，不要求该表情在发送用候选目录中。每页最多20项，每轮共享8次页面尝试预算。只有实际调用此工具的回合才将模型轮次上限提高至10，为分页后的最终回复留出机会，原有总超时不变；其他回合仍使用原轮次上限。每次真正取页之前都重新 `get_msg` 核验本群范围、消息ID和发送者；中途取消不会继续请求或把迟到结果交给模型。查询必须在 `send_message`／`stay_silent` 之前进行，不能补查来支撑已经发出的断言。

底层使用 [`fetch_emoji_like`](https://github.com/NapNeko/NapCatQQ/blob/v4.18.28/packages/napcat-onebot/action/extends/FetchEmojiLike.ts)，保留原生结果码和分页标志，而不是把被截断的名单当完整结果。群聊返回的 `tinyId` 按 NapCat 的 QQ 用户标识映射为 `user_id`；已用实际群成员查询复核过该映射。只向模型提供QQ号和经过限长／控制字符清理的昵称，不暴露头像URL、原始分页cookie或服务端错误正文；昵称不构成身份或权限凭据。

返回 `users` 为本页新增回应者，`seen_users` 为本条查询链累计去重数，`complete` 表示是否无遗漏地遍历到明确末页。`has_more`／`next_cursor` 指示是否继续；模型游标是本轮独有的不透明标识，绑定消息、表情、类型和可选目标QQ，不能跨查询或跨轮复用。原生协议有时需要在最后一个非空页后再读一个空末页，程序不会提前认定完成。

传了 `user_id` 时，`target_found=true` 表示已经在本条查询链任意一页找到目标，可直接停止分页；`false` 只在完整、无缺失的查询中未找到时返回，其他情况为 `null`。坏行、重复／停滞分页、缺失标志、预算耗尽等不会被解释为“这个人没点”。这只是本次读取的当前名单，不证明历史上从未点过，也不提供每人次数或点击时间，翻页期间名单可能变化。

重复请求复用本轮缓存。若本轮随后对同一消息／表情执行添加或取消（包括结果不明），对应名单缓存和旧游标失效，重新查询会从首页读取；不会清零页面预算，也不影响其他消息的游标。工具原始名单不另行写入数据库或摘要，程序不根据回应者身份提升管理权限。

## 图片

使用同一个 `[ai]` 模型的原生多模态能力，不配置第二个模型。模型需支持 Chat Completions 的 `image_url` 输入。

```toml
[images]
enabled = true
max_per_turn = 3
max_download_mb = 10
```

开启后可发图片并 @她，或引用图片消息再 @她。模型按需调用 `view_images`，程序将图片作为 Base64 `image_url` 内容块加入当轮请求，而不是让另一个模型转述。关闭时不暴露工具，也不下载、上传图片。

目前支持 JPEG、PNG、WebP、GIF（动画仅首帧）；单张最多10MiB、4000万像素，去除元数据并缩放到最长2048像素。仅获取可核验的本群附件和允许的 QQ HTTPS 图片地址，链接过期、下载失败或不支持的格式会返回不可读取错误，不允许猜图。数据库只保存图片ID和来源，不存原图、Base64或签名链接；原图仅当轮使用，之后需要时重新获取。

## 合并转发

```toml
[forward]
enabled = true
max_per_read = 20
```

开启后可发合并转发并 @她，或引用该消息再 @她。时间线记录引用ID和条数：卡片数字仅是“提示，未核实”，无可靠数字时标为未知，查询后以返回节点数为准。模型通过 `read_forward({forward_id,start,end})` 读取从1开始、包含两端的范围；每次最多20条，返回实际范围、下一条位置和截断说明。

嵌套只展示 `[合并转发 fwdn_…]`，需要再次调用工具，不自动向模型展开。[NapCat 接口](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/go-cqhttp/GetForwardMsg.ts) 没有服务端分页，底层可能一次取回含嵌套的完整包，程序仅在当轮缓存并切片。最多3层、每轮6次有效读取、120条；成功页面合计最多29500字符，错误说明另受工具轮数限制。单包1MiB、当轮缓存2MiB，过大内容会拒绝或明确截断。

仅接受本群近期消息及其直接引用的转发ID；子ID只在读到对应页后开放。转发中的发送者只是 `claimed_sender`，不能代表主人授权；内部消息ID不用于群管理或引用发送。转发内图片本版仅占位，不支持查看。关闭时不提供读取工具、不查询转发资源。数据库仅保存根引用和数量元数据，不保存转发原包或资源ID；被回复引用的文字仍可能进入普通群记忆。日志仅记录范围、数量、耗时和错误码。

## 日志与排查

默认 `info` 级别，终端可读输出 + `data/logs/` 中的 JSONL 文件；配置见 `[logging]`。按 UTC 天或20MiB轮转，写入时清理超过7天或总量200MiB的旧日志。目录700、文件600；只支持一个 Bot 实例写入同一目录。

```sh
npm run logs -- --follow               # 最近记录并持续跟随
npm run logs -- --level warn           # 警告及错误
npm run logs -- --turn t_0123456789abcdef # 替换为实际 turn_id
npm run logs -- --directory data/logs  # 配置损坏时仍能查看
```

查看命令读取有界尾部（每文件256KiB、最近200个文件），默认最多显示100条，可用 `--lines` 调整。`turn_id` 串联触发、模型、工具和发送；`turn.end` 的 `outcome` 区分 `replied`（已回复）、`silent`（主动沉默）、`prose_suppressed`（模型未调用发送工具）、`cancelled`（重置、断线、停止或超时取消，不因新消息取消）、`model_failed`、`delivery_unknown`（不要盲目重发）及 `round_limit`。

模型日志包含耗时、HTTP错误分类和服务商返回的合法 token 用量；图片日志区分来源核验、DNS、下载、解码。`debug` 额外显示普通消息被跳过的原因，修改级别后需重启。**所有级别都不记录聊天正文、人设、模型内容、图片、密钥、签名链接、管理确认码或群名片内容**，但含 QQ／消息ID，请勿随意公开。写入故障或队列满会丢弃日志并限频警告，不影响 Bot；控制台阻塞不会拖住文件日志。

## 小提醒

- 只服务配置中的白名单群，私聊不处理；主人仍固定为 `src/contracts.ts` 的 `OWNER_ID`，不会随群配置改变。
- 管理能力使用 `off`／`confirm`／`direct` 三态，禁言上限仍不能超过600秒；修改配置后需要重启。
- `/ping` 检查在线，`/help` 查看帮助；主人可用 `/reset` 清空记忆、`/confirm 确认码` 确认操作。
- 随机回复默认概率3%，在 `[reply] random_probability` 调整；触发不保证发言。`reply.mention` 控制被@触发，`tools.mention` 控制发送@。
- AI 启用后，本群上下文会发送给模型服务商；启用图片或转发阅读后，按需查看的图片和转发页面也会发送，请事先告知群成员。
- 本地记忆放在 `data/`；密钥、配置备份和数据库不要提交。
